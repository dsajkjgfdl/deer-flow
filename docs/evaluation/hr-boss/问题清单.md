# 记录1

数据库里一个员工对应多条“当前岗位”，主要不是查询写错，而是 **`employee_change` 表本身是变动流水/任职历史表，不是已经唯一化的当前状态表**。

我查了 `employee_change`：

- 表里没有唯一约束保证“一个员工只能有一条 `结束日期 LIKE '2199%'` 的当前记录”。
- `2199` 只是“未关闭/当前有效”的标记，但源数据里有些旧岗位、兼职岗位、组织调整岗位也没有被关闭。
- 所以同一个员工可能同时有多条 `2199` 记录。

统计结果：

| 每人 `2199` 当前记录数 | 员工数 |
| ---------------------: | -----: |
|                   1 条 |   4053 |
|                   2 条 |     35 |
|                   3 条 |      5 |
|                   4 条 |      2 |

按不同当前岗位数看：

| 每人不同当前岗位数 | 员工数 |
| -----------------: | -----: |
|               1 个 |   4060 |
|               2 个 |     31 |
|               3 个 |      4 |

典型原因有两类：

1. **兼职/兼岗**
   例如 `employee_change.变动类型 = '兼职'` 的记录也可能是 `结束日期=2199...`，所以员工会同时挂多个岗位。

2. **组织调整/调动后旧记录未关闭**
   例如一个员工从“销售工程师”调整为“总监助理”，但旧的“销售工程师”记录仍然是 `2199`，于是 SQL 会认为两个岗位都当前有效。

006 差异里的例子：

```text
yuangong1838:
MySQL 当前岗位 = 销售工程师、总监助理
图谱当前岗位 = 总监助理

yuangong1674:
MySQL 当前岗位 = 副经理、研发工程师
图谱当前岗位 = 研发工程师

yuangong3573:
MySQL 当前岗位 = 会计、经理、财务经理
图谱当前岗位 = 会计
```

所以原因可以总结为：

**MySQL 原始 `employee_change` 中存在未收口的多条当前有效岗位记录；图谱构建时已经把当前岗位收敛为一个主岗位关系 `CURRENTLY_IN_POSITION`，而 SQL 直接按所有 `2199` 记录分组，导致一个员工被计入多个岗位。**

后续 SQL 如果要和图谱一致，不能只用：

```sql
ec.`结束日期` LIKE '2199%'
```

还需要先定义“主当前岗位”的选择规则，比如排除 `兼职`，或按某个字段/日期/图谱构建口径只取一条当前岗位。



# 记录2

013 不一致的原因是 **SQL 和 Cypher 用的“专业”口径不一样**。

CSV 中：

- SQL 查的是 `employee_info.最高专业 LIKE '%电子信息工程%'`，结果 `70`
- Cypher 查的是教育经历节点 `EducationExperience.major = "电子信息工程"`，结果 `67`

我按员工编号做了集合差异，结果是：

| 类型        | 人数 | 原因                                                         |
| ----------- | ---: | ------------------------------------------------------------ |
| 两边都命中  |   65 | `最高专业` 和教育经历里都有精确的“电子信息工程”              |
| SQL 多出    |    5 | 这些人的 `最高专业` 是“电子信息工程技术”，被 SQL 的 `LIKE '%电子信息工程%'` 模糊匹配进来了，但 Cypher 精确等于“电子信息工程”，所以不算 |
| Cypher 多出 |    2 | 这些人教育经历里有“电子信息工程”，但 `employee_info.最高专业` 分别是“软件工程”“计算机科学与技术”，所以 SQL 不算 |

关键样本：

```text
SQL 多出的 5 人：
最高专业 = 电子信息工程技术
教育经历专业 = 电子信息工程技术

Cypher 多出的 2 人：
最高专业 = 软件工程 / 计算机科学与技术
教育经历专业包含 = 电子信息工程
```

我还用 MySQL 按 Cypher 口径复核了一下：

```text
education.专业 = '电子信息工程' 的当前员工数：67
```

这和 Cypher 的 `67` 完全一致。

所以结论是：**013 不是执行错误，而是口径不一致**。  
如果问题“当前电子信息工程专业员工”按教育经历精确专业理解，SQL 应改用 `education.专业 = '电子信息工程'`，结果应为 `67`。如果业务希望把“电子信息工程技术”也算进去，那 Cypher 也要改成 `ed.major CONTAINS '电子信息工程'`，但那会变成更宽的模糊专业口径。
