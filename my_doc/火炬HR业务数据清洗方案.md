# 火炬 HR 业务数据清洗方案

## 1. 分析范围

本文档基于本地 MySQL `huoju_hr` 库当前已落库的 17 张 HR 业务表做字段画像和清洗建议。`hr_interviewnotes` 因接口当前无业务数据，导入脚本已排除，不纳入清洗范围。

## 2. 总体清洗原则

保留原始层：导入表中的 `raw_payload` 和原中文业务字段应保留，不直接覆盖。建议新增清洗层表或视图，例如 `stg_hr_baseinfo`、`dwd_employee_current`。

统一空值：将 `NULL`、空字符串、纯空格、`无`、`未知`、`未填写`、`N/A` 等统一为数据库 `NULL`。但对于二值业务字段，不能随意把缺失当作“否”，应保留 `未知` 或 `NULL`。

统一日期：当前大部分日期为 `yyyy-MM-dd HH:mm:ss` 字符串，应清洗为 `DATE` 或 `DATETIME`。年份类字段统一提取四位年份整数。

识别哨兵日期：
- `1900-01-01`、`1899-12-31` 多半是未知开始日期或系统默认值，需要标记为 `is_default_date=1`。
- `2199-12-31`、`9999-12-31` 多半表示“至今/长期有效”，不要当作真实结束日期参与年龄、任期、区间最大值统计，应转为 `end_date = NULL` 并增加 `is_current=1`。

统一员工主键：`hr_baseinfo.员工编号` 当前 4582 条全量唯一，应作为员工主键。其他表的员工编号均未发现无法回连基础信息的孤儿编号，但部分表存在少量缺失员工编号，必须进入异常记录。

保护隐私字段：身份证、手机号、邮箱、家庭住址、联系人电话、社会关系姓名等字段只在权限内使用。分析层应尽量脱敏，例如身份证保留校验结果和出生日期派生，不直接暴露全号。

统一枚举字典：性别、婚姻状况、政治面貌、学历、职称级别、用工类型、用工关系状态、合同状态、绩效等级、奖惩类型、协议签署状态等应建立字典表。

文本标准化：组织、部门、职位、毕业学校、专业、单位名称、项目名称、职称内容、职业资格等字段需要 trim、全半角归一、括号归一、去除异常换行，并建立别名映射。

## 3. 跨表主数据规则

### 3.1 员工主数据

建议构建 `dim_employee`：

- 主键：`员工编号`
- 基础字段来自 `hr_baseinfo`
- 当前组织、部门、职位、用工关系状态优先来自 `hr_employeechangerecords` 最新有效区间
- 入职信息补充来自 `hr_onboardinginfo`

清洗校验：

- `员工编号` 必须非空且唯一。
- `员工姓名` 可以用于展示，但不能作为关联键。
- 子表存在员工编号缺失时，不参与员工画像主链路，进入异常表。
- 关联 ID 当前在多表可作为源系统人员内部 ID，真实数据中 `hr_baseinfo.关联ID` 为 4582 个 distinct / 4582 行；但业务主键仍以 `员工编号` 为准，`关联ID` 只作为接口追踪和辅助核验字段。

### 3.2 时间区间

涉及开始/结束日期的表包括员工变动、合同、项目、社会工作经历。统一规则：

- `开始日期 <= 结束日期`，否则进入异常。
- 结束日期为 `2199-12-31` 或 `9999-12-31` 时按“当前有效/至今”处理。
- 当前记录优先取 `结束日期 IS NULL` 或最大结束日期为哨兵值的记录。

### 3.3 当前员工口径

当前员工从 `hr_employeechangerecords` 最新记录推导，不直接用 `hr_baseinfo` 全量人数：

- 每个员工按 `开始日期`、`结束日期` 排序取最新有效记录。
- `用工关系状态` 为 `正式员工`、`试用员工`、`实习`、`返聘`、`劳务派遣-正式` 时计入当前员工。
- `劳务派遣`、`临时工`、`劳务工`、`待分配`、`顾问`、`辞职`、`离职`、`实习终止`、`辞退`、`退休`、`返聘终止` 等状态不计入当前员工；其中 `待分配` 作为未定岗/复核状态单独关注。

### 3.4 组织架构口径

`hr_organizationalstructure` 按“当前有效员工-组织路径快照”处理，不应简单视为部门字典或员工当前部门宽表：

- `员工编号` 可稳定回连 `hr_baseinfo`，当前未发现孤儿员工编号。
- `组织架构` 使用 `_` 拼接层级，建议拆解为集团、公司、中心/事业部、部门、科室/车间、班组等层级字段，同时保留原始完整路径。
- `组织` 是员工所属组织/法人或公司口径；`组织架构` 的第二层通常也是公司层级，但存在不一致样本，不能用其中一个字段强行覆盖另一个字段。
- 同一员工可能存在多条组织路径，应全部保留并标型，区分上级/下级重复、矩阵兼职和跨组织异常；不能默认收敛为单一当前部门。
- 当前组织、中心、部门/小组等组织层级筛选优先使用 `hr_organizationalstructure.组织架构` 解析出的组织树；`hr_employeechangerecords.部门` 保留为变动记录部门，用于历史变动、兼容展示和交叉校验。
- 当前岗位、用工状态仍由 `hr_employeechangerecords` 的最新有效记录推导。

## 4. 逐表清洗建议

### 4.1 `hr_baseinfo` 员工基础信息

画像结论：

- `员工编号` 4582 条全量唯一，是最可靠员工主键。
- `组织` 缺失 123 条；性别缺失 124 条，出生日期/年龄缺失 125 条。
- 身份证信息缺失 126 条，其中存在空字符串，需要统一空值。
- 邮箱缺失 2150 条，现居住地缺失 2090 条，属于高缺失联系信息。
- 入司日期最小值为 `1900-01-01`，需作为默认/异常日期处理。

清洗规则：

- `员工编号`：trim，统一大写；为空则进入异常表。
- `员工姓名`：trim，仅用于展示和人工核对，不作为主键。
- `组织`：建立组织标准名字典；缺失时可从最新变动记录的部门/组织链补齐，但补齐来源要记录。
- `性别`：标准化为 `男`、`女`、`未知`。
- `出生日期`：转 `DATE`；根据身份证和出生日期交叉校验。
- `年龄`：建议不长期保存为权威字段，使用出生日期按统计日期重算；源字段保留为 `source_age`。
- `入司日期`：转 `DATE`；`1900-01-01` 标记为默认日期，不参与司龄计算。
- `司龄(年)`：建议按清洗后的入司日期重算，源字段保留为 `source_tenure_years`。
- `年龄分段`：建议由清洗后年龄重新派生，避免源年龄和分段不一致。
- `身份证信息`：校验 18 位格式、出生日期、性别位、校验码；对外只保留脱敏值。
- `手机号码`：校验 11 位手机号；无效号码进入异常字段。
- `电子邮箱`：校验邮箱格式；缺失率较高，不作为员工识别依据。
- `是否涉密`：缺失不能默认为“否”，应清洗为 `是/否/未知`。

### 4.2 `hr_educationexperience` 教育经历

画像结论：

- 员工编号缺失 3 条；无孤儿员工编号。
- 候选组合键 `员工编号 + 入学时间 + 毕业时间 + 毕业学校 + 学历 + 专业` 有 4 组重复。
- `学校类型` 缺失 2208 条，缺失率约 61.0%。
- 真实数据中出现 `大专以下` 学历值；清洗层将其排序为 20，低于 `大专` 的 30。
- `入学时间` 存在 `1899-12-31`，疑似默认日期。
- `毕业时间` 最大到 2027 年，可能包含在读或预期毕业信息。

清洗规则：

- 缺失员工编号的教育记录进入异常，不参与人员画像。
- 对重复教育经历按完整字段去重；如仅时间或专业缺失不同，不自动合并。
- `最高学历` 清洗为布尔字段；`最高学历=1` 视为源系统确认的当前最高，同一员工多条为 1 时进入异常复核。
- `学历` 建立等级字典，例如博士、硕士、本科、大专、中专/高中等。
- `学历形式`、`学习方式` 建字典，缺失保留未知。
- `毕业学校`：trim、统一括号、去除多余空格；后续可接学校别名字典。
- `学校类型`：由于缺失率高且暂不要求源系统补数，只作为加分标签，不作为硬筛选条件。
- `入学时间`、`毕业时间` 转日期；`1899-12-31` 标记为默认未知。
- 若毕业时间晚于当前日期，标记为 `is_expected_graduation=1`。

### 4.3 `hr_healthrecordinfor` 健康档案

画像结论：

- 员工编号无缺失，无孤儿员工编号。
- 候选键 `员工编号 + 年份 + 体检类型` 无重复。
- `年份` 存在 `2023年`、`2023.12.6` 等非纯年份写法。
- `体检结果` 最长 893 字，属于敏感健康文本。

清洗规则：

- `年份` 提取四位年份整数；含具体日期的值保留原值到 `source_year_text`，标准年份取年份部分。
- `体检类型` 建字典，例如入职体检、年度体检。
- `体检结果` 作为敏感健康信息，默认不进入通用问答明细；可抽取是否异常、异常关键词等脱敏标签。
- 健康表权限应高于普通 HR 画像表。

### 4.4 `hr_employeechangerecords` 员工变动记录

画像结论：

- 12597 行，是推导当前岗位、部门、用工关系状态的核心表。
- 员工编号缺失 5 行；无孤儿员工编号。
- 候选键无重复。
- `变动原因` 缺失 5348 行，缺失率约 42.5%。
- `结束日期` 最大为 `2199-12-31`，明显是当前有效区间哨兵值。

清洗规则：

- 员工编号缺失记录进入异常。
- `开始日期`、`结束日期` 转日期；`2199-12-31` 转为 `NULL` 并标记 `is_current=1`。
- 同一员工按开始日期排序生成任职区间，检查区间重叠。
- `部门`、`职位` 建标准字典，去除空格、括号差异和历史命名差异。
- `用工关系状态` 建字典；`正式员工`、`试用员工`、`实习`、`返聘`、`劳务派遣-正式` 计入当前员工，其余劳务临时、待分配、离开或终止类状态不计入。
- `变动类型` 建字典，统一入职、调动、离职、转正等口径。
- `变动原因` 缺失较多，只做补充说明，不作为强规则。

### 4.5 `hr_employeecontract` 与 `hr_othercontracts` 合同信息

画像结论：

- 两张表均 34 行，经业务字段比较，当前内容完全一致。
- `合同编号` 均唯一。
- `合同期限`、`甲方单位` 两字段 100% 缺失。
- `结束日期` 缺失 5 条。

清洗规则：

- 建议只保留一张合同事实表，例如 `fact_employee_contract`，来源可同时记录两张表名。
- 若后续接口语义确认不同，再拆分员工劳动合同和其他协议合同。
- `合同期限`、`甲方单位` 当前不进入清洗层主表，可保留在原始层；除非源系统补数。
- `合同编号` 作为合同主键。
- `合同类别` 当前只有单一值，可保留但不作为分析维度重点。
- `合同状态` 建字典，例如生效、终止。
- 结束日期缺失的合同需根据合同状态判断是否仍有效。

### 4.6 `hr_onboardinginfo` 入职信息

画像结论：

- 员工编号缺失 7 行；无孤儿员工编号。
- `员工编号` 候选键有 1 组重复，共 7 行，可能是缺失员工编号造成的重复组或源系统重复。
- 高缺失字段较多：介绍人 94.5%、面试情况 50.4%、岗中体检项目 88.3%、廉洁协议书/保密协议 71.1%。

清洗规则：

- 员工编号缺失行进入异常。
- 每名员工保留一条入职信息；重复记录按 `关联ID` 或 `raw_payload` 差异人工复核。
- `用工类型` 建字典，并和变动记录中的 `用工关系状态` 做一致性校验。
- `入职来源` 建来源渠道字典。
- 协议字段统一为 `已签署/未签署/未知`，缺失不能自动视为未签署。
- 体检字段统一为 `已完成/未完成/未知`。
- `面试情况`、`介绍人` 属于补充文本或人员信息，高缺失，不作为核心筛选条件。

### 4.7 `hr_emergencycontact` 紧急联系人

画像结论：

- 员工编号缺失 7 行；无孤儿员工编号。
- 紧急联系人姓名和电话缺失约 33.6%。
- 候选键有 1 组重复，共 5 行。

清洗规则：

- 作为隐私表，默认不进入普通分析宽表。
- 员工编号缺失行进入异常。
- 联系人姓名 trim；电话只保留格式校验结果和脱敏号码。
- 电话字段统一去除空格、横线、括号；校验手机号或固定电话格式。
- 重复联系人按 `员工编号 + 联系人姓名 + 联系人电话` 去重。

### 4.8 `hr_performancerecord` 绩效记录

画像结论：

- 员工编号无缺失，无孤儿员工编号。
- 候选键 `员工编号 + 考核年份` 无重复。
- `主管评价` 缺失 3216 条，缺失率 99.7%。
- 考核年份存在 `2023年` 与 `2023` 混用。

清洗规则：

- `考核年份` 提取四位年份整数。
- `考核结果` 建绩效等级字典，并拆出排序分值，例如 S > A > B > C > D。
- 含 `D待改进`、`D不胜任`、`D不合格` 等要保留细分标签，不要简单合并为 D。
- `主管评价` 当前几乎不可用，暂不要求源系统补数，只保留原始层，不进入核心画像。
- 同一员工同一年度只能有一条绩效记录。

### 4.9 `hr_rewardpenaltiesrecord` 奖惩记录

画像结论：

- 员工编号无缺失，无孤儿员工编号。
- 候选键无重复。
- `奖惩级别`、`奖惩单位` 100% 缺失。
- `奖惩类型` 缺失 30.7%，`奖惩内容` 缺失 8.6%。

清洗规则：

- `奖惩时间` 转日期。
- `奖惩类型` 建字典，区分奖励、违纪、处分等；缺失时可从奖惩内容关键词辅助分类，但需标记为推断。
- `奖惩内容` trim，保留原文本。
- `奖惩级别`、`奖惩单位` 当前不进入清洗层主表。

### 4.10 `hr_socialworkexperience` 社会工作经历

画像结论：

- 员工编号缺失 2 行；无孤儿员工编号。
- 候选键无重复。
- `工作描述` 缺失 90.4%。
- `结束日期` 最大为 `9999-12-31`，明显表示至今。

清洗规则：

- 员工编号缺失行进入异常。
- `开始日期`、`结束日期` 转日期；`9999-12-31` 转为 `NULL` 并标记 `is_current=1`。
- 单位名称、任职职务做文本标准化，可后续建立公司/岗位别名字典。
- `工作描述` 高缺失，不作为必备字段；有值时可做关键词抽取。

### 4.11 `hr_socialrelation` 社会关系

画像结论：

- 员工编号缺失 1 行；无孤儿员工编号。
- 候选键无重复。
- 工作单位缺失 38.2%，联系电话缺失 31.2%。

清洗规则：

- 作为强隐私表，默认不进入普通问答画像。
- 员工编号缺失行进入异常。
- `与本人关系` 建字典，例如父亲、母亲、配偶、子女、兄弟姐妹等。
- 关系人姓名、联系电话脱敏。
- 工作单位做文本标准化，但不作为核心业务筛选字段。

### 4.12 `hr_socialhonor` 社会荣誉

画像结论：

- 员工编号无缺失，无孤儿员工编号。
- 候选键无重复。
- `是否为高层次人才` 当前只有单一值，分析区分度较低。
- `到期时间` 缺失 22 条。

清洗规则：

- `荣获时间`、`到期时间` 转日期。

## 8. 已确认业务口径

1. 当前员工口径：`用工关系状态` 为 `正式员工`、`试用员工`、`实习`、`返聘`、`劳务派遣-正式` 时计入当前员工；`劳务派遣`、`临时工`、`劳务工`、`待分配`、`顾问` 及辞职、离职、终止、退休、辞退等状态不计入。

3. 哨兵日期口径：`1900-01-01`、`1899-12-31` 视为未知/默认日期；`2199-12-31`、`9999-12-31` 视为至今/当前有效结束日期。
4. 合同口径：`hr_employeecontract` 与 `hr_othercontracts` 在清洗层合并为一张合同事实表，并保留来源表追溯。
5. 敏感字段口径：健康档案、社会关系、紧急联系人、身份证、电话、地址等不开放原文明细，只进入脱敏汇总、校验结果或标签层。

7. 组织架构口径：`hr_organizationalstructure` 代表当前有效组织路径快照，用于组织树、员工组织路径、当前组织/中心/组织单元筛选和当前组织校验；`dim_department` 只代表变动记录部门字典。
8. 多组织路径口径：同一员工多条 `组织架构` 路径全部保留并标型，区分 `hierarchy_duplicate`、`matrix_or_parttime`、`cross_org_review`；当前主部门仍按员工变动记录推导。

### 9.3 组织路径与“组织多路径”说明

数据库里没有单独建一个叫“组织多路径”的中文表。“组织多路径”落在 `fact_employee_org_path` 表中，通过 `path_relation_type` 字段表达。

`dim_org_path` 负责描述组织路径本身，例如：

- `org_path_id`：完整组织路径的稳定 ID。
- `org_path`：完整组织路径原文。
- `level_1` 到 `level_6`：按 `_` 拆出来的层级。
- `depth`：组织路径层级深度。

`fact_employee_org_path` 负责描述员工和组织路径的关系，例如：

- `employee_id`、`employee_name`：员工。
- `org`：源数据中的组织字段。
- `org_path_id`、`org_path`：员工关联到的组织路径。
- `path_relation_type`：多路径类型。
- `org_company_mismatch`：`组织` 与 `组织架构` 第二层不一致时标记为 1。

当前 `path_relation_type` 分布如下：

| path_relation_type | 当前行数 | 含义 |
|---|---:|---|
| `current_path` | 4458 | 员工只有一条有效组织路径，或未识别为多路径关系。 |
| `cross_org_review` | 1 | `组织` 字段和 `组织架构` 第二层公司不一致，需要跨组织复核。 |
| `matrix_or_parttime` | 0 | 当前真实数据暂未出现跨部门/跨中心多路径；规则保留。 |
| `hierarchy_duplicate` | 0 | 当前真实数据暂未出现上级/下级重复路径；规则保留。 |

查看“组织多路径”明细时，应查 `fact_employee_org_path`：

```sql
SELECT employee_id, employee_name, org, path_relation_type, org_path
FROM fact_employee_org_path
WHERE path_relation_type IN (
  'matrix_or_parttime',
  'hierarchy_duplicate',
  'cross_org_review'
)
ORDER BY employee_id, path_relation_type;
```

查看多路径类型统计：

```sql
SELECT path_relation_type, COUNT(*)
FROM fact_employee_org_path
GROUP BY path_relation_type
ORDER BY COUNT(*) DESC;
```

### 9.6 第一版边界与第二层衔接

- 奖惩、面试、健康、社会关系等低频、敏感或需要更多业务口径确认的事实表。
- 学校、专业、项目、单位、荣誉、资格名称的别名治理。
- 健康结果、面试情况、工作描述、主要职责等长文本的关键词或标签抽取。
- 面向知识图谱的节点/关系重建，以及 Text2Cypher profile 更新。

## 10. 第二层清洗层落地说明

第二层清洗层是在第一版 P0 基础上继续补充的 P1 业务事实层。它仍由 `backend/scripts/clean_huoju_hr_mysql.py` 统一生成，读取本地 MySQL `huoju_hr` 库中的原始 `hr_*` 表，并通过 `DROP + CREATE` 重建清洗层表。原始接口表不做修改。

第二层的目标不是做最终宽表，而是把分散在各接口里的业务记录先结构化为“可关联、可统计、可追溯”的事实表和字典表：

- 可关联：所有员工相关事实尽量使用 `employee_id` 关联 `dim_employee`。
- 可统计：学历、绩效、职称等常用维度增加标准等级或排序字段。
- 可追溯：事实表保留 `raw_payload`，用于审计和后续字段扩展。
- 不强行补数：高缺失字段保留原值和缺失状态，不作为强筛选条件。

### 10.2 字典表说明

第二层新增的 `dim_org_unit`、`dim_department`、`dim_position`、`dim_employment_status`、`dim_education_level`、`dim_performance_grade`、`dim_title_level` 是轻量字典表，主要用于后续统计、筛选和问答候选值展示。

其中 `dim_org_unit` 是新版组织架构主字典，来自 `hr_organizationalstructure.组织架构`，按完整路径逐级展开：

- `org_unit_name`：当前组织节点名称。
- `org_full_path`：从集团顶层到该节点的完整路径。
- `parent_org_unit_id`、`parent_org_full_path`：父级组织节点。
- `org_name`：路径第二级，通常为子公司/本部组织。
- `center_name`：路径第三级，作为“部门分布”默认中心层级口径。
- `depth`：组织节点所在层级。

`dim_department` 只代表员工变动记录中的部门原值，主要用于历史变动、兼容展示和与组织树交叉校验。涉及当前部门、中心、小组、班组的人数、名单、分布和筛选时，应优先使用 `dim_org_unit` 或 `dws_employee_profile` 中来自组织树的字段。

这些字典表当前不做别名归并。例如 `销售工程师(北京)` 与 `销售工程师（北京）` 会作为两个源系统原值保留。原因是 MySQL 默认排序规则可能把全角括号和半角括号判为相等，导致字典主键冲突；清洗层已将相关自然键字段设置为二进制排序规则，优先保证源值不丢失。后续如果要把这些值合并为同一个标准岗位，应单独建立别名映射表，而不是在第一轮清洗时自动合并。

### 10.3 员工变动事实说明

`fact_employee_change` 来自 `hr_employeechangerecords`，用于表达员工历史或当前的部门、职位、用工状态变化：

- `change_id`：基于原始行生成的稳定 ID。
- `employee_id`、`employee_name`：员工关联字段。
- `department`、`position`：变动记录中的部门和职位原值。
- `change_type`：变动类型。
- `employment_status`：用工关系状态。
- `start_date`、`end_date`：变动起止日期。
- `is_current_interval`：结束日期为 `2199-12-31` 或 `9999-12-31` 时标记为 1，表示当前有效区间。
- `is_current_employee_status`：用工状态属于 `正式员工`、`试用员工`、`实习`、`返聘`、`劳务派遣-正式` 时标记为 1；`待分配` 不计入当前员工，仅作为未定岗/复核状态。

这里要区分两个概念：`is_current_interval` 代表这条变动记录是否“当前有效”，`is_current_employee_status` 代表这条记录的用工状态是否属于“当前员工”口径。一个看时间区间，一个看业务状态。

### 10.4 教育经历事实说明

`fact_education` 来自 `hr_educationexperience`，用于表达员工的多条教育经历：

- `education_level`：学历原值。
- `education_level_rank`：学历排序值，例如博士高于硕士，硕士高于本科；当前排序为博士 70、硕士 60、本科 40、大专 30、大专以下 20。
- `major`、`school`、`school_type`：专业、毕业学校、学校类型。
- `is_highest_education`：`最高学历=1` 时标记为 1，视为源系统确认的当前最高学历。
- `enrollment_date`、`graduation_date`：入学和毕业日期。
- `is_default_enrollment_date`：入学时间为 `1900-01-01` 或 `1899-12-31` 时标记为默认日期。
- `is_expected_graduation`：毕业日期晚于当前日期时标记为 1，可理解为预计毕业或未来日期。

同一员工如果出现多条 `最高学历=1`，不会在清洗层直接猜测哪条是真正最高，而是进入 `dq_hr_cleaning_errors` 复核。当前数据未发现该类异常。

### 10.5 绩效事实说明

`fact_performance` 来自 `hr_performancerecord`，用于表达员工年度考核结果：

- `assessment_year`：从 `考核年份` 中提取年份。
- `performance_result`：考核结果原值。
- `performance_grade`：从考核结果中抽取 S/A/B/C/D 等级。
- `performance_grade_rank`：绩效等级排序值，S 最高，D 最低。
- `manager_comment_present`：只标记主管评价是否填写，不把主管评价作为强筛选条件。

如果同一员工同一年出现多条绩效记录，清洗层会保留记录并写入异常复核。当前数据未发现该类异常。

### 10.6 职称、资格和项目事实说明

`fact_job_title` 来自 `hr_jobtitleinfo`，用于表达员工职称记录：

- `title_name`：职称内容。
- `title_level`、`title_level_rank`：职称级别及排序值。
- `is_highest_title`：`最高职称=1` 时标记为 1。
- `certificate_no`、`issuer`、`awarded_date`：证书编号、评定单位和授予时间。

`fact_professional_qualification` 来自 `hr_professionalqualification`，用于表达职业资格记录。`qualification_level` 缺失率较高，当前只保留原值，不作为强筛选条件。

`fact_project_experience` 来自 `hr_projectexperience`，用于表达项目经历：

- `project_name`：项目名称。
- `project_role`：担任角色。
- `start_date`、`end_date`：项目起止日期。
- `is_current_project`：结束时间为 `2199-12-31` 或 `9999-12-31` 时标记为 1。
- `responsibility_present`：只标记主要职责是否填写；职责正文暂不做关键词抽取。

### 10.7 第二层异常说明

第二层清洗后，`dq_hr_cleaning_errors` 当前共 8 条：

| source_table | error_type | 当前行数 | 说明 |
|---|---|---:|---|
| `hr_employeechangerecords` | `missing_employee_id` | 5 | 员工变动记录缺少员工编号，无法关联到员工主表。 |

### 10.8 第二层后续仍未处理的内容

第二层事实表已经可以支撑常见 HR 画像和结构化问答，并已进一步汇总为第一张服务层员工画像宽表。当前仍未处理：

- 学校、专业、项目、岗位、资格名称的同义词和别名归并。
- 奖惩、面试、健康、社会关系等更敏感或低频事实表。
- 项目职责、工作描述、主管评价等长文本的标签化和关键词抽取。
- 面向 Text2Cypher、知识图谱或领导问答的图谱重建和 profile 更新。

### 10.9 真实数据切换后的复核结论

接口切换到真实数据并重建清洗层后，清洗方案需要做以下同步调整：

1. 行数画像全部更新为真实数据口径。当前 `dim_employee` 为 4582 人，当前员工为 2497 人，清洗层事实表也随真实数据扩容。
2. 组织多路径处理规则继续保留，但当前真实数据几乎都是单路径：`current_path` 4458 条，`cross_org_review` 1 条，暂未出现 `hierarchy_duplicate` 和 `matrix_or_parttime`。
3. 组织路径缺失异常本轮已消失，`dq_hr_cleaning_errors` 当前只保留 8 条 `missing_employee_id`；这些记录虽然缺员工编号和姓名，但仍有岗位、学历或 `关联ID` 等业务字段，不能静默丢弃。
4. `hr_baseinfo` 中仍有 123 名员工未出现在组织架构表，其中 1 名为当前正式员工，应进入组织覆盖率复核。
5. 学历字典新增真实值 `大专以下`，清洗层已将其排序为 20，低于 `大专` 的 30，避免后续学历排序把两者视为同级。
6. 用工状态字典从 11 个扩展到 16 个；当前员工口径已重新确认，计入 `正式员工`、`试用员工`、`实习`、`返聘`、`劳务派遣-正式`，不计入 `劳务派遣`、`临时工`、`劳务工`、`待分配`。
7. 本轮已新增 `dws_employee_profile` 员工画像宽表，当前 4582 行，与 `dim_employee` 一致。
8. 组织树主口径已对齐 `text2cypher-profile.md`：当前组织/中心/组织单元优先来自 `hr_organizationalstructure.组织架构`；`dim_department` 降级为变动部门字典。当前 `dim_org_unit` 为 488 个节点，`department_org_unit_mismatch=1` 的员工为 32 人。

## 11. 第三层员工画像宽表落地说明

第三层清洗层当前新增 `dws_employee_profile`，它是第一张面向问答和画像使用的服务层宽表。它不替代第二层事实表，而是把常用字段先汇总到“一人一行”，减少每次问答都跨多张事实表拼接的成本。

### 11.1 表粒度与当前行数

`dws_employee_profile` 的粒度是每个员工编号一行，当前共 4582 行，与 `dim_employee` 保持一致。当前员工口径仍沿用已确认规则，`is_current_employee=1` 共 2497 人：

| 用工状态 | 当前员工人数 |
|---|---:|
| 正式员工 | 2238 |
| 试用员工 | 161 |
| 实习 | 56 |
| 返聘 | 26 |
| 劳务派遣-正式 | 16 |

### 11.2 汇总字段来源

画像宽表当前汇总以下字段：

- 员工主数据：来自 `dim_employee`，包括员工编号、姓名、所属组织、当前部门、当前职位、用工状态和当前员工标记。
- 组织路径摘要：来自 `fact_employee_org_path`，包括主组织路径、路径数量、是否有组织路径、是否多路径、是否跨组织复核。
- 当前组织树字段：来自主组织路径解析，包括 `current_org_name`、`current_center_name`、`current_org_unit_name`、`current_org_full_path`。其中 `current_center_name` 作为部门分布默认中心层级口径，`current_org_unit_name` 是员工当前组织路径叶子节点。
- 部门交叉校验：`department_org_unit_mismatch` 标记变动记录部门与组织路径叶子节点是否不一致，当前 32 人为 1；该字段只用于复核，不自动覆盖任一来源。
- 最高学历：来自 `fact_education`，优先取 `is_highest_education=1` 的记录，再按学历排序和毕业日期兜底。
- 最新绩效：来自 `fact_performance`，按考核年份取最新记录，同年再按绩效等级排序兜底。
- 最高职称：来自 `fact_job_title`，优先取 `is_highest_title=1` 的记录，再按职称级别和授予日期兜底。
- 资格和项目数量：分别来自 `fact_professional_qualification` 与 `fact_project_experience`，当前只汇总数量，不展开明细。

### 11.3 组织路径与数据质量标签

组织路径仍保留第二层多路径口径，画像宽表只做摘要，不把多路径员工强行压成一个业务结论。主组织路径优先选择 `current_path`，其后才是 `hierarchy_duplicate`、`matrix_or_parttime`、`cross_org_review`。

部门/组织筛选口径参照 HR Boss Agent 的 `text2cypher-profile.md`：当前组织、中心、部门、小组、班组等组织层级筛选优先走组织树字段，不使用 `dim_department.department_name` 作为主筛选入口。用户问“部门分布”“员工部门分布”等默认按 `current_center_name` 汇总；只有用户明确要求最细部门、小组或班组时，才使用 `current_org_unit_name` 或完整组织路径继续细分。

`data_quality_flags` 是 JSON 数组，当前用于标记：

| 标签 | 当前人数 | 说明 |
|---|---:|---|
| `no_org_path` | 123 | 员工主表中存在，但组织架构接口没有对应路径。 |
| `cross_org_review` | 1 | 组织字段和组织架构第二层公司不一致，需要复核。 |
| `multi_org_path` | 0 | 当前真实数据未出现同员工多条组织路径，但规则保留。 |
| `has_cleaning_error` | 0 | 当前 8 条清洗异常均缺员工编号，无法挂到具体员工画像行。 |

没有质量标签的员工 `data_quality_flags` 为空数组。当前共有 4458 人没有首个质量标签。

### 11.4 使用边界

`dws_employee_profile` 适合回答“当前员工中本科及以上多少人”“某部门员工最新绩效分布”“具备职称或项目经历的人有哪些”等常见筛选和统计问题。涉及学历明细、历史绩效趋势、多条项目经历、资格明细时，仍应回到第二层事实表查询。

敏感字段仍不进入画像宽表。健康、社会关系、紧急联系人、身份证、电话、地址等字段继续只允许进入脱敏汇总、校验结果或标签层，不开放原文明细。
