# HR Boss Text2Cypher Profile

## 适用范围

当前 Text2Cypher 服务用于 HR Boss Agent 的人力资源图谱问答。所有 Cypher 生成、校验、执行和修复都必须遵守本 profile 中的业务口径。

## 默认范围与高风险澄清规则

对于人数、平均年龄、平均司龄、名单、排名、占比、筛选、年龄、工龄、职称、证书等精确员工统计问题，优先沿用用户在当前问题或会话中明确给出的公司、组织或部门范围。未给出范围时，默认按全集团当前员工统计，并在 `assumptions` 中说明采用了该默认范围，不得仅因为缺少公司名而中断查询。

部门分布默认按全集团当前员工范围、中心层级口径汇总；用户明确指定其他范围或最细部门层级时再按用户要求处理。只有具体人员身份冲突、明显不同的公司/项目/证书等实体冲突，或不同选择可能显著改变结论时，才返回 `status=needs_clarification`。

## 员工预设筛选口径

员工预设查询支持性别、职称、部门、组织单元、中心层级、岗位、子公司、学历、院校层次、专业、项目、绩效、学校名称、年龄范围和司龄范围等筛选条件，并始终限定为当前员工。不同维度之间按 AND 组合，同一维度内多个选中值按 OR 组合。
不要使用 OrgUnit 判断当前员工；当前员工身份必须由 Employee 当前状态和当前任职关系口径判断。OrgUnit 只用于组织层级筛选和向下包含子级组织。
年龄范围使用 `Employee.age`，司龄范围使用 `Employee.tenure_years`。`max_age` 是整数年龄的包含式上限；用户说“年龄 40 岁以下”时按 `max_age=39` 处理，不包含 40 岁。用户说“入职满 5 年以上”或“司龄 5 年以上”时按 `min_tenure_years=5` 处理，包含 5 年。

性别筛选使用 `genders`，学校名称筛选优先使用 `school_names`；旧参数 `schools` 仅作为兼容别名。部门、中心、车间、小组、班组等组织层级筛选使用 `org_units`，并沿组织单元层级向下包含子级组织；用户明确要求中心层级归属时使用 `center_names`，按 `OrgUnit.center_name` 匹配。绩效只匹配最近一期考核记录，并使用清洗层标准等级 `PerformanceAssessment.performance_grade` 的 `S/A/B/C/D`，不要用 `assessment_result` 做等级筛选；项目匹配全部项目经历，不只匹配当前项目。职称、岗位、专业和项目等匹配证据只在用户实际使用对应筛选条件时返回。

组织当前人数快速查询与同范围员工名单快速查询必须使用完全相同的当前员工、组织范围和筛选条件口径。人数模式只返回去重后的当前员工人数，不加载员工卡片。

员工基础档案和结构化详情按用户原始人员标识查询，并在 `Employee.employee_id` 与 `Employee.employee_name` 上做精确匹配。工具入参必须来自用户原文或上一轮工具结果中的员工标识，不得根据历史上下文、数字顺序或脱敏样例命名规律推断、递增、换算或替换员工编号。员工编号唯一命中时直接返回；精确姓名命中多名员工时必须返回候选并要求澄清，不得任意选择。员工基础档案允许查询历史员工，但必须明确返回是否属于当前员工；不得默认返回电话、社会关系等敏感字段。查询具体员工教育背景、绩效记录、工作经历、项目经历、资格证书、职称信息、岗位变动记录、荣誉奖惩或全部信息时，应通过员工档案工具的 `sections` 选择对应详情。

职称、岗位、学历、院校层次和专业可按可解释的相关候选扩展；部门、组织单元、中心层级、子公司、项目和学校存在多个高风险候选时必须澄清；绩效等级只接受 `S/A/B/C/D` 精确匹配。预设查询返回的 `selected_values` 是最终采用的标准值，不能由回答层自行替换。

## 高学历和教育筛选口径

用户询问“高学历员工”“高学历人才”“硕士及以上员工”且没有进一步限定院校层次时，默认按任一教育经历中的学历层级为硕士或博士处理，以 `EducationExperience.degree` 为准，并在回答中说明“本次按硕士及以上口径查询”。该口径不是专业口径，不得使用 `EducationExperience.major`。

用户询问“985”“211”“985/211”“双一流”“名校”等院校层次或学校背景时，按任一教育经历中的院校层次处理，以 `EducationExperience.school_type` 为准，并在回答中说明采用的院校层次口径。该口径不是专业口径，也不是学校名称口径；不得把 `985`、`211`、`双一流`、`硕士`、`博士` 作为 `majors` 参数。

只有用户明确询问专业方向、专业名称或学科专业时，才使用 `EducationExperience.major`。

## 字段值纠错转换口径

Text2Cypher 的正常领导问答使用单次查询规划：模型同时理解用户问题、选择图谱中的真实字段值、判断风险并生成 Cypher。低层 `resolve_terms` 仅用于独立评测或排障，不属于正常回答链路。

同一业务类别的多个相关部门或岗位候选应合并查询，并在 `assumptions` 中说明实际采用的范围；不得仅因为存在多个相关候选而要求用户确认口径。只有高风险实体冲突才允许追问。没有可靠候选时不得编造字段值。

## 具体人员实体口径

具体人员扩展查询包括全部信息、教育背景、绩效记录、工作经历、项目经历、资格证书、职称信息、岗位变动记录、荣誉奖惩等。生成 Cypher 时必须先按用户原始人员标识在 `Employee.employee_id` 和 `Employee.employee_name` 上做精确匹配，再连接对应的教育、绩效、工作、项目、证书、职称、变动或荣誉关系；不得把真实姓名当作 `Employee.employee_id`，也不得根据旧脱敏编号样例推断员工编号。如果只按一个字段查询为空，应改为双字段精确匹配后再判断 `not_found`，不得把结构化字段未返回误写成系统无法查询。
不得只把 `yuangong...` 或真实姓名当作 `Employee.employee_id`；这类值只能作为用户原始人员标识进入双字段精确匹配或候选澄清。

当前生产员工编号来自清洗层 `dim_employee.employee_id`，是字符串字段，可能是纯数字、前导零编号或含字母/连字符编号，例如 `000937`、`001505`、`HJ1621`、`RT-0032`、`AMC-0865`、`SULD0130`。生成查询时必须保留用户输入中的前导零、字母大小写和连字符，不得把员工编号转成整数。

当用户用“中文姓名/称呼 + 空格 + 数字”指代具体员工时，应同时保留人员姓名候选并做无空格规范化。例如“老王 166”可作为 `Employee.employee_name = "老王166"` 的候选查询，不应只按裸数字查询工号。若用户只给出裸数字 `937`，不得直接等同于 `000937`；需要通过候选召回或澄清确认后，才可使用补零后的完整员工编号。

用户询问“基本信息、岗位、绩效”等员工档案信息时，“岗位”是需要返回的字段，不是岗位筛选值；不得因为“岗位”未命中 `Position.position_name` 字段值而触发术语澄清或中断查询。

## 分组和排名口径

排名或分组统计默认只统计有效维度值。Top N 问题也按这个口径处理。

除非用户明确要求统计“未填写”“未知”或空白项，否则分组字段必须排除：

- null
- 空字符串
- 仅包含空格的字符串
- 未填写
- 未知
- 无
- N/A

学校、部门、岗位、职称、证书、专业等维度进入 COUNT、ORDER BY、LIMIT 前，应先过滤无效值。

如果执行结果中排名或分组维度列出现 null、空字符串、未填写、未知等无效维度值，必须视为结果质量问题。遇到质量问题时，不要直接返回结果，应修复 Cypher，重新校验并重新执行。

上述默认过滤规则不适用于用户明确要求统计无效值的场景。用户问“专业为空”“专业为无”“专业未填写”等问题时，应保留空值、空字符串和 `无` 条件，并按教育经历 `EducationExperience.major` 统计当前员工去重；不得使用不存在的 `Employee.major` 属性，也不要改写为员工主数据最高专业口径。

## 职称和岗位口径

“高级工程师”在当前 HR 图谱中属于 Title（职称）口径，不属于 Position（岗位）口径。

用户问“中高级职称”时，默认按“中级及以上职称”处理，即 Title.title_level 必须包含 `中级`、`副高级`、`正高级`。不要把“中高级职称”简化成仅统计 `副高级`、`正高级`，也不应因为“中高级职称”没有匹配到单个职称名称而触发澄清。

用户问以下问题时，应优先使用 Title 节点或职称字段查询，不应优先使用 Position：

- 高级工程师有多少人
- 高级工程师有哪些
- 高级工程师名单

如果按 Position 查询不到记录，应自动改用 Title 口径重新查询。

## 人岗推荐和瓷粉研发候选人口径

当用户提出“推荐人”“候选人”“人岗匹配”“我需要一个研发经理”“从集团推荐一个瓷粉研发的人”等人岗推荐问题，并同时出现瓷粉、陶瓷、介电材料、MLCC、无机非金属材料等材料研发方向时，应按所有当前员工范围召回候选，不要把“集团”“全集团”“从集团”解析为具体 `Organization` 实体，也不要因为“研发经理”“瓷粉研发方向”没有匹配到单个岗位或职称字段值而中断查询。

这类问题的结构化候选应优先基于当前岗位、当前部门、教育经历专业、工作经历、项目经历、资格证书和职称等字段做轻量筛选和排序，返回候选员工编号、姓名、当前岗位、当前部门、当前组织、学历/学校/专业、职称、资格、相关工作经历或项目经历等可解释依据；候选数量默认按用户要求的 Top N，未明确时返回 5-10 人。

## 组织口径

当用户在组织限定中说“股份”“股份公司”或“福建火炬电子科技股份有限公司”时，应映射到数据库中的组织名 `福建火炬电子科技股份有限公司（本部）`，作为该组织的明确别名处理，不应触发组织澄清。生成 Cypher 时应追加 `Employee.current_org_name = "福建火炬电子科技股份有限公司（本部）"` 或等价的 `Organization.org_name = "福建火炬电子科技股份有限公司（本部）"` 组织过滤；涉及 `OrgUnit` 层级筛选时，优先使用实际存在的 `OrgUnit.org_name`、`OrgUnit.full_path` 或员工当前组织字段值，不要因为只匹配不带“（本部）”的公司名而返回 0。

福建火炬电子科技股份有限公司（本部）是火炬电子集团下一级的本部/子公司口径，不是集团母公司口径；它下面是中心、部门、小组等内部组织层级，不应表述为“福建火炬电子科技股份有限公司及其下属子公司”。

用户问“子公司”“各子公司”“公司”“组织”“单位”等分组统计时，统一视为组织维度；图谱侧优先使用 `Employee.current_org_name` 作为当前组织/子公司字段。该类泛化维度词不是具体组织名称，不应触发术语澄清。问题只给出组织分组维度、没有给出统计范围时，默认按全集团当前员工统计，并在 `assumptions` 中说明范围。

## 组织层级筛选口径

集团 HR 图谱的 `OrgUnit.full_path` 组织路径按“集团_子公司_子公司内组织层级...”排列。`火炬电子` 是集团顶层；其下一级通常是子公司或本部组织，例如 `福建火炬电子科技股份有限公司（本部）`；再往下才是该子公司内部的中心、部门、小组等组织单元。解析 `OrgUnit.full_path` 或生成组织层级筛选时，不要把顶层 `火炬电子` 当作子公司，也不要把子公司下的中心、部门误判为公司。用户指定子公司范围时，应优先匹配路径中的第二级组织或员工当前组织字段；用户指定中心、部门、小组时，应在对应公司/子公司范围下继续使用 `CONTAINS_ORG_UNIT*0..` 向下包含所有子级组织单元。

当前员工口径和组织层级筛选口径必须分开处理。

当前员工只由 `Employee.is_current_employee = true` 判断。`CURRENTLY_IN_DEPARTMENT`、`CURRENTLY_IN_POSITION` 和 `CURRENTLY_ASSIGNED_TO_ORG_UNIT` 只用于连接当前部门、岗位或组织单元，不再作为当前员工判断条件。不要仅使用 `BELONGS_TO_ORGANIZATION`、`Employee.current_org_name`、`OrgUnit` 关系或组织路径判断当前员工，因为离职或历史员工也可能保留组织归属信息。

当用户确认按部门口径查询时，仍必须使用 `OrgUnit` 层级筛选对应的部门、中心、车间、小组或班组。`Department` 只可作为兼容展示或历史变动参考，不得使用 `Department.department_name`、`Department.org_name` 或 `CURRENTLY_IN_DEPARTMENT` 关系上的 `Department` 节点作为部门名称筛选入口，也不要生成 `MATCH (e)-[:CURRENTLY_IN_DEPARTMENT]->(d:Department) WHERE d.department_name ...` 这类部门筛选 Cypher。即使 term resolution 将“研发”“IT部”等词映射到 `Department` 候选，只要用户确认的是部门/组织层级口径，生成 Cypher 时也应改用 `CURRENTLY_ASSIGNED_TO_ORG_UNIT` + `CONTAINS_ORG_UNIT*0..`，并通过 `OrgUnit.org_unit_name`、`OrgUnit.full_path` 或实际存在的 OrgUnit 字段筛选。
`Department` 只可用于当前员工口径判断、兼容展示或历史变动参考，不得作为当前组织筛选主入口。

用户问“部门分布”“员工部门分布”“某类员工的部门分布”等分组统计时，默认按 `OrgUnit.center_name` 聚合，作为面向领导汇报的中心层级口径；不得按 `Employee.current_department_name` 聚合，也不得按 `Department.department_name` 聚合，以免小组、班组、科室等过细层级导致分布碎片化。只有用户明确要求“按最细部门”“按小组/班组/科室分布”时，才使用更细的组织层级字段；逐人明细中可以展示员工当前部门字段，但分布聚合仍优先使用 `OrgUnit.center_name`。标准形态为：先按当前员工口径限定员工，再匹配 `CURRENTLY_ASSIGNED_TO_ORG_UNIT` 的当前组织叶子，使用 `leaf.center_name` 做分组字段，并按分组有效值规则过滤空值、`未填写`、`未知`、`无`、`N/A`。回答口径说明应写为“按中心口径/中心层级汇总”或“按中心归属汇总”，不要表述为“当前所属部门”，避免让用户误解为按最细部门字段聚合。

`OrgUnit` 组织树负责解释“中心、部门、车间、小组、班组”等组织层级归属。用户问“某中心/某部门/某车间/某小组的人数、名单、平均值、职称、证书、排名、占比”等员工统计问题时，优先使用 `CURRENTLY_ASSIGNED_TO_ORG_UNIT` + `CONTAINS_ORG_UNIT` 做组织架构层级筛选，并向下包含所有子级组织单元；不要只用 `Department.department_name` 精确匹配作为新版组织架构下部门查询的唯一口径。

生成 Cypher 时，应先限定当前员工，再按组织树筛选员工当前组织架构路径。标准形态为：员工通过 `CURRENTLY_ASSIGNED_TO_ORG_UNIT` 指向当前所在叶子或本级组织单元，目标组织单元通过 `CONTAINS_ORG_UNIT*0..` 向下包含该组织单元。`*0..` 用于同时包含目标组织单元本级和所有下级组织单元。

```cypher
MATCH (e:Employee)
MATCH (e)-[:CURRENTLY_ASSIGNED_TO_ORG_UNIT]->(leaf:OrgUnit)
MATCH (target:OrgUnit)-[:CONTAINS_ORG_UNIT*0..]->(leaf)
WHERE coalesce(e.is_current_employee, false) = true
  AND target.org_unit_name = "IT部"
RETURN count(DISTINCT e) AS employee_count
```

如果用户同时给出公司或组织范围，例如“股份公司 IT部有多少人”，应在当前员工范围内追加公司/组织过滤，同时继续使用 `OrgUnit` 层级筛选 IT部。股份公司本部在数据库中的组织名为 `福建火炬电子科技股份有限公司（本部）`，生成查询时应使用该实际存储值：

```cypher
MATCH (e:Employee)
MATCH (e)-[:CURRENTLY_ASSIGNED_TO_ORG_UNIT]->(leaf:OrgUnit)
MATCH (target:OrgUnit)-[:CONTAINS_ORG_UNIT*0..]->(leaf)
WHERE coalesce(e.is_current_employee, false) = true
  AND (
    e.current_org_name = "福建火炬电子科技股份有限公司（本部）"
    OR target.org_name = "福建火炬电子科技股份有限公司（本部）"
    OR target.full_path CONTAINS "福建火炬电子科技股份有限公司（本部）"
  )
  AND target.org_unit_name = "IT部"
RETURN count(DISTINCT e) AS employee_count
```

例如员工实际挂在 `火炬电子_福建火炬电子科技股份有限公司（本部）_信息管理中心_IT部_软件开发组`，查询 `IT部员工` 时必须把 `软件开发组` 下的当前员工纳入统计。`Department` 可以作为兼容旧图谱或补充展示的口径，但当 schema 中存在 `OrgUnit`、`CURRENTLY_ASSIGNED_TO_ORG_UNIT` 和 `CONTAINS_ORG_UNIT` 时，部门/中心/小组筛选必须优先走组织架构树。

## IT 人员口径

用户询问“IT人员”“IT人才”“信息技术人员”“信息化人员”等 IT 相关人员群体的人数、名单、分布、占比、排名或其他统计时，`数据中心研发部` 不属于 IT 人员口径。即使部门、岗位或术语候选将该部门识别为 IT 相关，也必须从结果中排除当前组织位于 `数据中心研发部` 本级及其所有下级组织单元的人员。

排除时应使用员工的当前 `OrgUnit` 组织路径或组织树关系判断，不得只按 `Department.department_name` 排除。标准形态为先匹配员工通过 `CURRENTLY_ASSIGNED_TO_ORG_UNIT` 指向的当前组织叶子，再排除被 `数据中心研发部` 通过 `CONTAINS_ORG_UNIT*0..` 包含的叶子；回答中的 `assumptions` 必须说明“IT 人员统计已排除数据中心研发部及其下级组织”。

该排除规则只适用于 IT 相关人员群体的语义识别和统计。用户明确询问“数据中心研发部”的人数、名单、组织分布或其他部门自身情况，或明确要求将该部门纳入统计时，应按用户指定范围正常查询，不得应用上述排除规则。

## 当前员工口径

用户查询中的“员工”“人员”“公司人数”“部门人数”“平均年龄”“名单”等默认全部指当前员工。除非用户明确指定离职、辞职、历史、曾任或变动记录，否则不得把 `Employee.is_current_employee` 不为 true 的员工纳入统计。

当前员工的主口径为：`coalesce(e.is_current_employee, false) = true`。当前部门、当前岗位、当前组织单元关系只用于组织/岗位筛选和展示；有 1 名当前员工可能缺少组织路径或岗位关系，因此不能用这些关系存在性替代当前员工标记。

对于人数、平均值、名单、排名、占比、筛选、年龄、工龄、职称、证书等精确员工统计问题，如果用户未明确指定公司、组织或部门，也未明确指定“全集团”“全部公司”“所有当前员工”等全局范围，不得默认限定到福建火炬电子科技股份有限公司（本部）；应默认按全集团当前员工生成查询，并在 `assumptions` 中说明范围。

除非用户明确询问“涉密”“保密”“非涉密”或指定要排除涉密员工，否则当前员工统计不得默认追加 `Employee.confidential_flag` 过滤条件。保密标识不是通用在职员工过滤条件。`Employee.confidential_flag` 仅为清洗层 `hr_baseinfo.是否涉密` 的 `是/否/空` 标记，不包含身份证、电话、地址等敏感原文明细。

标准 Cypher 口径（用户明确指定“全集团”“全部公司”“所有当前员工”等全局范围时）：

```cypher
MATCH (e:Employee)
WHERE coalesce(e.is_current_employee, false) = true
RETURN count(DISTINCT e)
```

生成涉及员工明细、聚合、排名、分组或筛选的 Cypher 时，应先把上述当前员工过滤条件放在员工范围限定中，再追加其它条件。只有用户明确指定组织、部门、公司或岗位时，才追加对应组织关系、部门关系或岗位关系过滤。继续使用 `DISTINCT e` 避免教育、绩效、职称、组织等明细关系造成重复计数。

查询平均年龄、平均司龄等员工级平均值时，应对当前员工范围内的唯一 `Employee` 节点计算平均值。若查询路径可能因为当前部门、当前岗位或其它明细关系重复同一员工，应先 `WITH DISTINCT e` 后再执行 `avg(e.age)`、`avg(e.tenure_years)` 等聚合，避免重复加权。

## 985/211 学校口径

“985员工”“985院校员工”“985毕业员工”默认按任一教育经历中的学校层次统计，以 `EducationExperience.school_type` 为准，不是组织、部门或学校名称口径，也不等同于最高学历院校。不得使用 `School.school_type` 统计 985/211 学校类型；学校节点上的同名属性属于冗余属性，不能作为员工教育经历的学校类型事实。除非用户明确询问“最高学历”“最高毕业院校”或类似口径，否则不得把该统计改写为最高学历口径。

用户询问“985”时，默认表示教育经历学校类型包含 985，既包括 `school_type = "985"`，也包括 `school_type = "985/211"` 等组合值。生成 Cypher 时应使用 `ed.school_type CONTAINS "985"`；不要使用学校节点 `s` 上的 `school_type` 属性，也不要只使用 `ed.school_type = "985"`。用户明确要求“仅985、不含211组合值”时，才允许使用精确匹配。

该口径是业务别名，不应触发澄清。只要问题语义是学校层次或教育背景，就应继续按 `EducationExperience.school_type` 口径生成查询。

统计“985员工”的人数、名单、分组或占比时，仍必须先套用当前员工口径，并使用 `DISTINCT e` 避免同一员工多条教育经历造成重复计数。


## 变动原因因果口径

当用户问“因为绩效不达标被辞退”“因为工作表现不佳被降职”“由于某原因离职”等因果问题时，不能只把绩效记录和雇佣变动记录拼在一起推断因果。必须依赖 `EmploymentChange.change_reason`、`EmploymentChange.record_json` 中明确的变动原因证据，或其他明确原因字段。若只能查到绩效结果、辞退/离职/降职状态，但查不到明确原因，应返回 `status=no_reliable_evidence`、`answerable=false`、`should_retry=false`，并在 `limitation` 中说明无法可靠证明因果关系，不要编造名单。

## 结果质量规则

对于人数、平均值、名单、排名、占比、筛选等精确问题，结果必须来自结构化图数据库查询，不得凭材料印象估算。

如果生成、校验、执行或修复后仍无法得到可靠结果，应返回失败或限制说明，不要编造答案。
